# Request handling

[← Architecture](../architecture.md)

This document covers the surface an agent author implements
(`AgentExecutor`, `RequestContext`, `TaskUpdater`) and the protocol
orchestration behind it (`RequestHandler` / `DefaultHandler`).

## The author's surface: `AgentExecutor`

Implementing an agent means implementing one behaviour:

```elixir
defmodule MyAgent do
  @behaviour A2A.Server.AgentExecutor

  @impl true
  def execute(%A2A.Server.RequestContext{} = ctx, updater) do
    text = A2A.Server.RequestContext.user_input(ctx)

    updater
    |> A2A.Server.TaskUpdater.start_work()
    |> A2A.Server.TaskUpdater.add_artifact(A2A.Types.Part.text("processing: #{text}"))
    |> A2A.Server.TaskUpdater.complete(A2A.Types.Part.text("done"))

    :ok
  end

  @impl true
  def cancel(%A2A.Server.RequestContext{} = _ctx, updater) do
    A2A.Server.TaskUpdater.cancel(updater)
    :ok
  end
end
```

Contract (mirrors the reference SDKs, enforced by `DefaultHandler`):

- `execute/2` runs inside the task's [execution process](process-model.md); it
  is never called concurrently for the same task.
- The executor **emits** events through the `TaskUpdater`; it does not return
  output. Returning `:ok` after emitting a terminal (or `input_required` /
  `auth_required`) status is the normal path.
- An unhandled raise is caught by the framework and transitions the task to
  `failed`.
- The first event a fresh execution emits must be a `task` or `message`
  (start-of-work), matching the reference contract.

### Why a `TaskUpdater` instead of a raw bus

The Python/JS SDKs hand the executor a raw event bus/queue and expect it to
construct correctly-shaped events. We hand it a **`TaskUpdater`** bound to the
task — a thin, ergonomic emitter that builds the right event struct, stamps
`task_id`/`context_id`, broadcasts on the PubSub topic, and persists, in one
call. This keeps agent code declarative and keeps event-shape correctness in one
tested place.

`TaskUpdater` API (sketch):

| Function | Emits |
| --- | --- |
| `start_work/1` | `working` status |
| `update_status/3` | arbitrary status + optional message |
| `add_artifact/3` | artifact-update event (append/last-chunk aware) |
| `complete/2` | terminal `completed` |
| `fail/2` | terminal `failed` |
| `reject/2` | terminal `rejected` |
| `cancel/2` | terminal `canceled` |
| `requires_input/2` | `input_required` (ends stream) |
| `requires_auth/2` | `auth_required` (stream stays open) |

## `RequestContext`

The read-side struct handed to the executor:

```elixir
%A2A.Server.RequestContext{
  message: %A2A.Types.Message{},      # the incoming message
  task_id: "…",
  context_id: "…",
  task: %A2A.Types.Task{} | nil,      # existing task, if this continues one
  user: %A2A.User{},                  # authenticated caller (see cross-cutting)
  requested_extensions: [".../ext"],  # negotiated extensions
  config: %{},                        # send configuration (accepted output modes, blocking, …)
  metadata: %{}                       # request metadata
}
```

Helpers such as `user_input/1` (extract text parts) and accessors keep executor
code terse. Task/context IDs are generated by a pluggable ID generator
(UUID default).

## Protocol orchestration: `RequestHandler` / `DefaultHandler`

`A2A.Server.RequestHandler` is a **behaviour** covering the full, transport-
agnostic RPC surface. Both the JSON-RPC and REST plugs call the *same* handler —
this is the boundary that keeps agent logic written once (see
[Transports](transports.md)).

| Callback | A2A method |
| --- | --- |
| `send_message/2` | `message/send` (blocking or non-blocking) |
| `send_message_stream/2` | `message/stream` (SSE) |
| `get_task/2` | `tasks/get` |
| `cancel_task/2` | `tasks/cancel` |
| `resubscribe/2` | `tasks/resubscribe` (SSE) |
| `list_tasks/2` | `tasks/list` |
| `set_push_config/2` … | `tasks/pushNotificationConfig/*` |
| `agent_card/1` | `.well-known/agent-card.json` |

`A2A.Server.DefaultHandler` is the batteries-included implementation. It is
configured at init with the executor module, the stores, the PubSub name, the
push sender, the user resolver, and the agent card — nothing global. Its core
responsibilities:

### `send_message` / `send_message_stream` flow

1. Resolve or generate `task_id` / `context_id`; load any existing task from the
   `TaskStore`; reject continuation of a terminal task.
2. Start (or look up) the [execution process](process-model.md) for the task and
   **subscribe to the topic before** the executor begins, so no early event is
   missed.
3. **Streaming:** map each event to a `StreamResponse` and yield it to the SSE
   plug; persist as it goes; the push sender (if configured) delivers in
   parallel as another subscriber.
4. **Blocking:** drain the event stream to the terminal/`input_required` event
   and return the final `Task` or `Message`. `auth_required` is special-cased:
   return a snapshot immediately while draining continues in the background
   (matches the JS SDK).
5. **Non-blocking (polling):** return on the first `task`/`message` event; the
   client polls `tasks/get` or attaches later via `resubscribe`.

### `drain_timeout`: blocking-only, SDK-side

`send_message/3` accepts an SDK-side `:drain_timeout` option that bounds how
long the blocking drain (over `A2A.Server.EventStream`) waits before giving up
on a task that never reaches a terminal/`input_required` event:

```elixir
DefaultHandler.send_message(server, request, drain_timeout: 30_000)
```

- The server-wide default is set via `A2A.Server.Supervisor` init opts
  (`drain_timeout: :infinity` unless overridden) and is available per request as
  `server.drain_timeout`.
- A caller may override it per call with the `drain_timeout:` option shown
  above; passing `:infinity` disables the timeout for that call.
- On expiry, `send_message/3` returns `{:error, %A2A.Error{code: :timeout}}`
  unless the store already shows a terminal task (a caught executor raise
  persists `failed` before the process exits, so that result is preferred over
  a spurious timeout — see `DefaultHandler.resolve_blocking/3`).
- This is deliberately **not** a field on the proto `SendMessageConfiguration`
  message — it is a local execution-control knob for this SDK's drain loop, not
  part of the A2A wire protocol, so it stays out of `A2A.Types.*` and out of the
  request payload entirely.
- `send_message_stream/2` and `resubscribe/2` do not use `drain_timeout` — they
  always run their `EventStream` with `idle_timeout: :infinity`, since a
  streaming/SSE consumer (not the drain loop) owns disconnect semantics; see
  [ADR-0009](decisions/0009-eventstream-termination.md).

### Result assembly

A result assembler folds the event stream into the current `Task` (artifacts
merged by `artifact_id`, history maintained, terminal tasks frozen), mirroring
the references' `ResultManager`/`ResultAggregator` — but the per-task
serialization it needs is provided by the execution process, not a global lock.
